Machine runner swarm

A clean container for every job, on the Docker hosts you already run

Self-hosted CircleCI machine runner 3 on Docker Swarm, for Linux and Windows Server. No Kubernetes. Signed releases. An experimental add-on runs each job in a Kata microVM.

Start on Linux Start on Windows Server

Why machine runner swarm

  • A clean container for every job

    A runner claims one job and exits, and Swarm starts a new container. No job inherits files from the last one.

    What a clean environment covers

  • A microVM per job

    Kata Containers classes give each job its own VM and kernel, on Swarm, on Linux amd64 nodes with KVM. Experimental.

    MicroVM jobs

  • Linux and Windows Server

    Linux amd64 and arm64, and Windows Server 2022 and 2025. Labels decide where each class runs. A mixed Linux and Windows cluster was verified by hand.

    Multi-node clusters

  • Jobs never hold the class token

    A token proxy holds the class tokens, and the runners hold a placeholder. The persistent classes are the exception.

    The token proxy

  • Runners that install and update themselves

    A distributor service installs the runner on every node, pins a tested version, and checks its SHA-256. Nothing to install on the hosts.

    The runner distributor

  • Scale by setting replicas

    A Swarm service is a resource class, and deploy.replicas sets how many jobs it runs at once.

    How a class maps to a service

Who it is for

Teams that run Docker hosts or Windows Server and do not want Kubernetes. Setup is a resource class, a token, two secrets and one docker stack deploy. It sits between a single machine runner (jobs share a host) and a Kubernetes container runner.

Use something else when:

  • You need no machines of your own: use CircleCI cloud executors.
  • You run Kubernetes: use container runner.
  • You need autoscaling, privileged or KVM jobs, or a full VM per job today: use the machine runner orchestrator.
  • You need CircleCI server, macOS, or hosts with no internet access: this project does not cover them.

The FAQ has the full comparison.

Your first job

  1. Create a resource class and a token with the CircleCI CLI.
  2. Download the release, start Swarm, create the secrets, and deploy the stack. Follow Quickstart on Linux or Quickstart on Windows Server.
  3. Run a sample job twice, and see a new container each time. Then point a real workflow at your class: examples/ has a job config for every class.

Install paths, operations, and security are in the documentation.

Known limits:

  • Capacity is fixed: no autoscaling, no node creation.
  • One token proxy runs on a manager. It is not highly available, so use three managers in production.
  • Containers share the host kernel.

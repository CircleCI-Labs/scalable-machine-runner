Install on Linux with Docker Swarm

This page describes how to deploy CircleCI machine runner 3 as a Docker Swarm stack on Linux. The steps cover a single node, and Multi-Node Clusters extends them to several nodes.

Note

If you can run Kubernetes, CircleCI recommends container runner for containerized jobs. CircleCI documents a plain machine runner 3 on Docker setup too. This page is a sibling of those pages for teams that run Docker Swarm and want a clean container for every job.

Status. This is a CircleCI Labs project, 0.x, and CircleCI support does not cover it. It is tested against CircleCI cloud only, and What is tested says how. Replicas are fixed: the stack does not add or remove nodes, and it does not scale to the queue.

The manual steps come first and use ordinary docker commands. Nothing is installed on a node by hand: the stack has a service that installs the runner on every node, and docker stack deploy is the whole install. The optional setup helper runs the same steps. For a first run, Quickstart on Linux is shorter.

Prerequisites

  • A CircleCI cloud organization and a user who is an organization admin. CircleCI server is not tested: CircleCI server says what is known.

  • The CircleCI CLI 1.4.0 or later, signed in. The commands on this page use its syntax (circleci --version prints the version). Pass --org <org>, the organization slug such as gh/my-org or its UUID: without it the CLI takes the organization of the git remote of the current directory, which in a clone of this repository is not yours.

  • One or more Linux nodes with a supported operating system:

    Operating systemArchitectureStatus in this repository
    Ubuntu LTSamd64, arm64Tested in CI on Ubuntu 26.04. On arm64, every pipeline checks that the stack installs the runner and starts, and probe jobs run on a real arm64 runner on main and smr-swarm/* branches
    RHEL 8 and later, and compatible distributionsamd64, arm64Steps documented, not tested in CI
    Any of the aboveppc64le, s390xCircleCI lists these architectures. CI only starts the distributor and the token proxy image under emulation: no job has run on them

  • Docker Engine 24 or later, running, with Swarm mode available. Podman cannot run Swarm.

  • Root access, or membership of the docker group. Docker and a Swarm join are all that a node needs: no runner, entrypoint, or tool is installed on a node.

  • A node clock that is synchronized with NTP. TLS to CircleCI fails silently when the clock drifts.

  • Outbound HTTPS access from each node to the hosts in Egress hosts, which include the release bucket of CircleCI (the runner download) and the registries that serve the stock image alpine (the distributor) and the token proxy image (Docker Hub). What needs internet lists everything. No inbound access is required. This release is not tested without internet access: Run the downloads from a mirror describes what a mirror replaces.

  • Enough CPU and memory for the services. The shipped file reserves 4 CPUs and 8 GB of memory in total, and replicas that do not fit stay pending. Size the limits has the numbers of every class.

  • Enough runner concurrency in your CircleCI plan for the replicas that you run. It limits how many jobs run at once, whatever the replicas: Capacity and concurrency describes the limits.

Membership of the docker group is equivalent to root on the node. Limit it to administrators.

Self-hosted runner terms agreement

If you install self-hosted runners through the web app, an organization admin must agree to the CircleCI Runner Terms first. If you install and use self-hosted runners through the CLI, you agree to them by doing so. CircleCI documents this in Self-hosted runner terms agreement. The page that the terms link opens may carry another title, such as “Self-Hosted Applications Terms”. Whether running the token proxy between your runners and CircleCI is covered by these terms is a question for your own review: this project does not give legal advice.

Get the files

Use a release, or clone the repository at a release tag. The paths on this page are relative to the root of the repository or of the extracted release bundle.

git clone --branch <release-tag> https://github.com/CircleCI-Labs/machine-runner-swarm.git
cd machine-runner-swarm

Each GitHub release carries these files, where <version> is the release number without the v:

FileContent
machine-runner-swarm-<version>.tar.gzThe bundle for Linux: the stack files, the entrypoint, the runner-distributor script, the setup scripts, the documentation, and the examples, without the tests
machine-runner-swarm-<version>.zipThe same bundle for Windows
SHA256SUMSThe SHA-256 checksum of both bundles
SHA256SUMS.sigstore.jsonA keyless cosign signature of SHA256SUMS

The bundle has a top-level VERSION file with the release number and a CHANGELOG.md with the notes of every release.

A release is the recommended source, because its stack files name the token proxy image of that release by tag and digest. A git clone of a tag or of the default branch, or a “Download ZIP”, works too: the stack files there name the image tag latest, which only a release moves and which is not a pin. Refer to The token proxy image.

The token proxy image

The token proxy is the one container that holds your class tokens (The token proxy). It is a published image, ccilabs/machine-runner-swarm-proxy on Docker Hub, and the stack file pulls it when you deploy. ccilabs is the Docker Hub organization of CircleCI Labs. The name is not the trust root: the signature check of Verify the token proxy image is. You install nothing for it. It is a static Go binary in a minimal base, runs as a non-root user with a read-only root file system, and one tag covers linux/amd64, linux/arm64, linux/ppc64le and linux/s390x, so the node that runs it can have any of them. Windows nodes get the Windows image from the same tag (Windows).

TagWhat it is
X.Y.ZThe image of a release. It never changes: pin this one
X.Y, XThe newest release of that minor or major line
latestThe newest release. It is the default of the stack files in a checkout, and only a release moves it
edgeThe newest commit of the main branch that passed the end-to-end tests. Use it to test main, not to run jobs that matter
sha-<12 characters>The image of one commit of the main branch, published before its tests have run

The stack file reads the image from MACHINE_RUNNER_SWARM_PROXY_IMAGE. A release bundle has the default ccilabs/machine-runner-swarm-proxy:<version>@sha256:<digest> (the tag, and the digest that Docker pulls), a checkout has ccilabs/machine-runner-swarm-proxy:latest. linux/setup.sh --deploy prints a warning when the variable is not pinned by digest, which is the case in a checkout. To use another image, set the variable in the environment of docker stack deploy: a digest for a pin, a registry of your own for an air gap, or a local build for development.

# development: build the image from the checkout, and name it
docker build -t machine-runner-swarm-proxy:dev proxy/
sudo env MACHINE_RUNNER_SWARM_PROXY_IMAGE=machine-runner-swarm-proxy:dev docker stack deploy -c deploy/runners.yaml runners

The image must be on the node that runs the proxy (a manager by default, or the node that you pin it to). A local build exists only on the node where you built it: build it there, or copy it with docker save machine-runner-swarm-proxy:dev | ssh <node> docker load. Docker pulls a published image by itself. Verify the token proxy image shows how to check its signature, and Upgrade the token proxy how to change its tag.

Verify a release

CircleCI signs SHA256SUMS with the OIDC token of the CircleCI job that makes the release. No signing key is stored anywhere. The signature proves that a job of this CircleCI project made the file, and the checksums prove that your download is the file the job made. You need cosign 3.1.3 or a later 3.x (CI signs and verifies with 3.1.3, and earlier versions are not tested), curl, jq, and GNU coreutils, in a bash shell. On Windows, refer to Verify a release.

The release is the latest release of the releases page: set version once to its number without the v, and read its notes. The first line is a placeholder, and the download fails while it is unchanged.

version=X.Y.Z

Then paste this block. It runs in a subshell and stops at the first failing check. Only a bundle that passes the signature, the ref, and the checksum is unpacked.

(
  set -euo pipefail
  base="https://github.com/CircleCI-Labs/machine-runner-swarm/releases/download/v${version}"
  curl -fsSLO "${base}/machine-runner-swarm-${version}.tar.gz" \
       -O "${base}/SHA256SUMS" \
       -O "${base}/SHA256SUMS.sigstore.json"

  # 1. the signature: the CircleCI project and pipeline definition of this repository signed SHA256SUMS
  cosign verify-blob SHA256SUMS --bundle SHA256SUMS.sigstore.json \
    --certificate-identity "https://circleci.com/api/v2/projects/7bbdbb66-6ba8-4f6c-982e-d4fb401ec257/pipeline-definitions/8b2a66db-3f28-5c80-88e4-03f4694b5b60" \
    --certificate-oidc-issuer "https://oidc.circleci.com"

  # 2. the ref: a job of any branch can sign with that identity, so the certificate must also say that the job ran for refs/heads/main
  #    (the long string is the OID 1.3.6.1.4.1.57264.1.14 followed by the value refs/heads/main)
  hex=$(jq -r '.verificationMaterial | (.certificate // .x509CertificateChain.certificates[0]).rawBytes' SHA256SUMS.sigstore.json \
    | base64 -d | od -An -v -tx1 | tr -d ' \n')
  grep -Eq '^([0-9a-f]{2})*2b0601040183bf30010e0411(0c|13)0f726566732f68656164732f6d61696e' <<< "${hex}" \
    && echo "signed for refs/heads/main" || { echo "NOT signed for refs/heads/main: stop"; exit 1; }

  # 3. the file: its checksum is in the signed list
  sha256sum -c SHA256SUMS --ignore-missing

  # only a verified bundle is unpacked
  tar -xzf "machine-runner-swarm-${version}.tar.gz"
  echo "RELEASE VERIFIED"
)

Continue only when the last line is RELEASE VERIFIED. Anything else, an error message or no output at all, means that the release is not verified: delete the downloaded files, and start again or ask in an issue. The ref check exists because the signing identity is the same for every branch, so the block reads the certificate extension 1.3.6.1.4.1.57264.1.14 (the OID in the long string) and fails unless its value is refs/heads/main. The pattern starts on a byte boundary, and ASN.1 tag 0c or 13 is the string type of the value.

Then change into the bundle:

cd "machine-runner-swarm-${version}"

What the three checks establish is limited. A valid signature and refs/heads/main mean that a job of this CircleCI project ran for the main branch of the repository and made these files. Whether anyone can change main without a review is a setting of the organization that owns the repository, and this page cannot check it. A ruleset for main describes what the project asks for.

  • The identity is the CircleCI project (7bbdbb66-...) and the pipeline definition (8b2a66db-...) that run this repository’s pipeline. The issuer https://oidc.circleci.com is the CircleCI OIDC issuer. Sigstore records every signature in a public transparency log.

  • To see the ref of a certificate, print it. The last line of the output ends with the ref, and a release comes from refs/heads/main.

    jq -r '.verificationMaterial.certificate.rawBytes' SHA256SUMS.sigstore.json | base64 -d \
  | openssl x509 -inform DER -noout -text | grep -A1 '1.3.6.1.4.1.57264.1.14:'

  • If the project or its pipeline definition is ever re-created, the definition ID changes, and this page gives the new value.

1. Create the resource classes

Create a namespace if your organization has none. Each organization can have one namespace, and orbs use the same one.

$ circleci namespace create <namespace> --org <org>

Create one resource class for each service in the stack file. The class name must equal the service name. The shipped file linux/stack/runners.yaml has one service, linux-default. For a first run, keep this name. To rename it, edit your copy of the file first (step 5), and then create the class and the secret under the new name. More classes come later, one resource class each, from the add-on stack files of step 5 or from Resource Classes.

$ circleci runner resource-class create <namespace>/linux-default --org <org> --generate-token

Each command prints a token once. Store each token in your secret manager. If you lose a token, create a new one with circleci runner token create <namespace>/<class> --nickname <nickname>.

2. Prepare each node

Run these steps on every node that runs services.

Ubuntu

  1. Install Docker Engine from Docker’s repository by following Install Docker Engine on Ubuntu.

  2. Confirm the engine runs.

    $ sudo systemctl enable --now docker
$ docker version

  3. Confirm the clock is synchronized. The command prints yes.

    $ timedatectl show -p NTPSynchronized --value

A single node needs no firewall change. Multi-node clusters open the ports in Inter-node ports.

RHEL

  1. Install Docker Engine from Docker’s repository by following Install Docker Engine on RHEL. The Podman packages that RHEL ships cannot run Swarm.

  2. Enable the service, and confirm the engine and the clock.

    $ sudo systemctl enable --now docker
$ docker version
$ timedatectl show -p NTPSynchronized --value

  3. Keep SELinux enforcing. The runner is in a Docker volume and not in a host directory, so no directory needs a label for it.

Note

CI does not run on RHEL, so these steps follow Docker’s documentation and have not been exercised in this repository.

3. Start Swarm

On a single node, start Swarm so that it listens on the loopback address only. Nothing is exposed to the network.

$ docker swarm init --advertise-addr 127.0.0.1 --listen-addr 127.0.0.1:2377
$ docker swarm update --task-history-limit 2

The second command keeps fewer stopped containers on the node (setup.sh --swarm-init does both). The node is a manager, and the token proxy runs on a manager by default, with no label. In a cluster, label the node that runs the proxy with machine-runner-swarm.proxy=true (docker node update --label-add machine-runner-swarm.proxy=true <manager node name>): runner services never run on a node with that label, so a job never shares a node with the proxy. On a single node, do not set it. With several managers, pin the proxy to one: refer to Where the proxy runs, and when it moves. Each finished job leaves a stopped container until Swarm prunes its task, and every stopped container keeps its writable layer on disk.

A node that listens on the loopback address cannot accept other nodes. For several nodes, initialize Swarm with a routable address instead. Refer to Multi-Node Clusters. A node that joins needs nothing else, because the distributor service starts on it by itself.

4. Create the secrets

Create one secret for each service in the stack file. The secret is a runner config file and holds only the token:

api:
  auth_token: <token>

The token proxy mounts these secrets at /run/secrets/<service>-token, owned by uid 65534 with mode 0400, and the runners never see them. The runners read one more secret, runner-placeholder-token, with a made-up token: create it once, with any value, in the same format. The stack mounts it at /run/secrets/circleci_runner_config.yaml, owned by the runner user (uid 2000) with mode 0400, and the runner reads it with --config. Only the persistent class mounts its own token in the runner. Every other setting is a CIRCLECI_RUNNER_* environment variable in the stack file.

Create the secrets with a hidden prompt, so that the token does not reach your shell history or the process list. This loop uses only POSIX features, so it works in bash, zsh, and dash. Do not replace it with read -rsp: that form is bash only, and zsh reads -p as a coprocess and fails, which leaves TOKEN empty and creates a secret without a token. The loop stops at an empty token.

for class in linux-default; do   # one class; add the names of the other classes you deploy
  printf 'Token for %s (hidden): ' "$class"
  stty -echo; IFS= read -r TOKEN; stty echo; echo
  [ -n "$TOKEN" ] || { echo "no token entered for $class" >&2; break; }
  printf 'api:\n  auth_token: %s\n' "$TOKEN" | docker secret create "$class-token" -
done
unset TOKEN
printf 'api:\n  auth_token: machine-runner-swarm-placeholder\n' | docker secret create runner-placeholder-token -

Run every docker command in these steps with sudo, or as a user in the docker group. Without either, docker cannot reach the daemon. The setup helper below does the same in one command: sudo linux/setup.sh --secret linux-default, and then printf %s machine-runner-swarm-placeholder | sudo linux/setup.sh --secret runner-placeholder for the placeholder.

The secret name is the service name plus -token. docker stack deploy fails with secret not found when a service references a secret that does not exist. Create every secret that the file references, or delete the services you do not need from your copy of the file. Each optional class in step 5 needs its own secret.

docker stack config prints the mode 0400 as 256, its decimal value.

5. Review the stack file

Copy the directory linux/stack to a directory of your own, deploy/, and keep it under version control. From here on you check and deploy your copy and never the shipped files, so an edit never touches the shipped files. For a first run, change nothing: the copy works as it is, and you review it later.

$ cp -r linux/stack deploy

The directory holds the stack files and the two scripts that they ship as Swarm configs, circleci-runner-entrypoint and runner-distributor.sh. The stack files name the scripts relative to themselves (file: circleci-runner-entrypoint), so keep the scripts in the same directory as the stack files. If you delete the add-on stack files that you do not use, keep runners.yaml and the two scripts.

Keep the service runner-distributor and the top-level configs: and volumes: in your copy: every class needs them. A Swarm config cannot change, so its name carries the first 12 hex digits of the SHA-256 of its file. If you edit the entrypoint or the distributor script, rename its config the same way: sha256sum <file> | cut -c1-12. Review these settings first. Refer to Resource Classes for the details.

SettingDefaultChange it to
Service namelinux-defaultYour resource class name
imagecimg/base:2026.10Your image, pinned by digest. Refer to Images
deploy.replicas2The number of concurrent jobs you need
deploy.resources2 CPUs and 4 GBThe size of one runner. Limits and reservations are equal
placement.constraintsnode.platform.os == linuxAdd architecture or zone constraints
x-distributor-envAn exact runner version (an exact pin: 3.1.13 in this release) with the SHA-256 values of its tarballs, major version 3, a check every 24 hoursNothing for a first run. A newer pin or a floating version, or a mirror, are variables of docker stack deploy and need no edit. Refer to Upgrade the runner on Linux

Check that the file parses. This needs no running Swarm.

$ docker stack config -c deploy/runners.yaml > /dev/null

The optional classes are separate add-on stack files. Add each with another -c flag, and pass the same list of files on every deploy (how the files merge). Each add-on stack file needs its own resource class and its own secret <service>-token.

FileServicePurpose
linux/stack/classes-extra.yaml (in deploy/ after the copy)linux-java, linux-hardenedAn image swap (cimg/openjdk) and a hardened class without sudo. They show how to add a class. Reserves 6 more CPUs and 12 GB. Refer to Resource Classes
linux/stack/docker-build.yaml (in deploy/ after the copy)linux-docker-buildBuilds images with the host Docker engine. Needs a labeled worker node. Refer to Docker Builds
linux/stack/microvm.yaml (in deploy/ after the copy)linux-microvm, linux-microvm-docker, and the DNS forwarder microvm-dnsRuns each job in a Kata Containers microVM. Needs KVM and a node setup. Refer to MicroVM jobs
linux/stack/persistent.yaml (in deploy/ after the copy)linux-persistentA long-lived runner with a named volume. Needs the node name edited in the file. Refer to Persistent mode

An add-on stack file repeats the common service settings of runners.yaml, because YAML anchors do not cross files. That includes the four keys that a class needs for the runner: user: "0", the entrypoint, the config entrypoint, and the volume runner-bin mounted read-only. It repeats the top-level configs: and volumes: too, so it also loads alone. When you change a common setting, such as stop_grace_period or the logging options, change it in every file that you use.

6. Deploy the stack

Deploy your copy of the file from step 5. The command returns before the replicas run, because docker stack deploy does not wait.

$ docker stack deploy -c deploy/runners.yaml runners

To add the optional classes, pass your copies of their files with more -c flags, and pass the same list on every later deploy:

$ docker stack deploy -c deploy/runners.yaml -c deploy/persistent.yaml runners

This command is the whole install. The service runner-distributor starts on every Linux node, also on a node that joins later (not on a microVM node: its classes download their own runner). It downloads the runner of CircleCI (the exact version that the stack file pins, the newest that CI tests), checks its SHA-256 against the values that the stack file carries for that version, and puts it in the volume runner-bin of the node. The service token-proxy pulls its image from Docker Hub. A runner container that starts first waits up to 120 seconds for it. To deploy with other distributor settings, for example a floating version such as 3.1 (the distributor ignores the default SHA-256 list of the pin and trusts the manifest, which is weaker), set them as variables of this command. A host with sudo drops the environment, so write sudo env MACHINE_RUNNER_SWARM_RUNNER_VERSION=3.1 docker stack deploy ..., or run the command as a user in the docker group. Refer to Upgrade the runner on Linux.

Verify the deployment

  1. List the services. Each shows the running and desired replicas.

    $ docker stack services runners
ID             NAME                        MODE         REPLICAS   IMAGE
...            runners_linux-default       replicated   2/2        cimg/base:2026.10
...            runners_runner-distributor  global       1/1        alpine:3
...            runners_token-proxy         replicated   1/1        ccilabs/machine-runner-swarm-proxy:...

    The distributor shows one task for each Linux node (a microVM node has none), so 1/1 on a single node and 3/3 on three.

  2. Check the tasks of a service. A task in the Running state is a runner that polls CircleCI.

    $ docker service ps runners_linux-default

  3. Check that the distributor installed the runner. Its log has a line such as runner-distributor: [ ok ] current -> versions/3.1.13: circleci-runner 3.1.13 linux/amd64 for each node. Refer to See what runs.

    $ docker service logs --tail 20 runners_runner-distributor

  4. Check that the runners connected. circleci runner instance list --org <org> --resource-class <namespace>/linux-default lists each replica with the status online, and the web app shows the same under Runners. A replica has a name of the form <node hostname>-<service>-<slot>, for example node1-linux-default-1.

  5. Run a job. Use examples/linux-hello.yml: it is a complete config, and the quickstart shows it. Run the workflow twice. After each job, Swarm shows a new task for the slot. The file examples/linux-jobs.yml has a job named clean-check that fails if anything from an earlier job is still present.

Optional: use the setup helper

linux/setup.sh performs the steps above with checks. It never prints the token, and every step is idempotent. It needs bash 4.4 or later. It installs nothing on a node: the service runner-distributor of the stack installs the runner.

StepEffect
--checkPreflight: Linux on amd64, arm64, ppc64le or s390x, Docker running and 24 or later, Swarm state, NTP
--swarm-initRuns docker swarm init on the loopback address unless Swarm is active, and sets the task history limit to 2. The node is a manager, which is where the token proxy runs
--secret <service>Creates the secret <service>-token from a token read on stdin
--deployRuns docker stack deploy with each --stack-file. Without one it deploys the shipped linux/stack/runners.yaml, so pass your copy from step 5. It warns when MACHINE_RUNNER_SWARM_PROXY_IMAGE is not pinned by digest

With no step, it runs --check. The steps always run in the order of the table, whatever order you type them, and the hint after every run starts with Next: and names only the steps that are still to do (the Swarm, the secrets linux-default-token and runner-placeholder-token, the stack), read from Docker. When nothing is left it starts with Check: and names the commands that show the runners start. Options are --stack-file (repeatable) and --stack-name.

sudo linux/setup.sh --check --swarm-init
sudo linux/setup.sh --secret linux-default   # a hidden prompt asks for the token
sudo linux/setup.sh --deploy --stack-file deploy/runners.yaml

Create one secret for every service of the stack files you deploy. --deploy fails with secret not found when one is missing. Every command needs sudo or membership of the docker group, because each one talks to the Docker daemon. The helper is a bash script with a #!/usr/bin/env bash line, so it runs from any shell, including zsh. To script one secret, pipe the token: printf %s "$TOKEN" | sudo linux/setup.sh --secret linux-default. Several --secret values need a terminal, because stdin carries one token.

The distributor reads its settings from the environment of --deploy: MACHINE_RUNNER_SWARM_RUNNER_VERSION, MACHINE_RUNNER_SWARM_RUNNER_MAJOR, MACHINE_RUNNER_SWARM_CHECK_INTERVAL, MACHINE_RUNNER_SWARM_DOWNLOAD_BASE_URL, and MACHINE_RUNNER_SWARM_RUNNER_SHA256, and for the token proxy the variables MACHINE_RUNNER_SWARM_PROXY_*. A host with sudo drops the environment, so to deploy with these variables, run sudo env MACHINE_RUNNER_SWARM_RUNNER_VERSION=3.1 linux/setup.sh --deploy, or run docker stack deploy as a user in the docker group. Refer to Upgrade the runner on Linux.

The helper accepts a token that has only letters, digits, ., _, and -, and it keeps an existing secret unchanged. To replace a token, refer to Rotate a runner token. The preflight warns when the clock is not NTP-synchronized. The helper does not label nodes. For a docker-build class, run docker node update --label-add machine-runner-swarm.docker-build=true <worker node> yourself.

Upgrade

With the default settings, the nodes run the exact runner version that the stack file pins, and a new release of the runner changes nothing until you change the pin or deploy a release of this repository that carries a newer one. Upgrade the runner and images covers the runner version, the images, and a roll back.

A new release of this repository changes the shipped stack files, and your copy deploy/ is not updated by itself. To merge:

  1. Read the notes of the release and the changelog: entries marked [BREAKING] say what to change. This is a 0.x project, so a minor release can change the files.

  2. Verify and unpack the new release beside the old one (Verify a release). The old release directory is the base of the merge. If you cloned a tag, use git worktree or a second clone for the old tag.

  3. See what changed between the two releases:

    diff -ru "machine-runner-swarm-${old}/linux/stack" "machine-runner-swarm-${new}/linux/stack"

  4. Merge each file that differs into your copy. A three-way merge takes your changes and the changes of the release, and reports a conflict where both changed the same lines. Keep deploy/ under version control, so that you can see and revert the result.

    git merge-file deploy/runners.yaml \
  "machine-runner-swarm-${old}/linux/stack/runners.yaml" \
  "machine-runner-swarm-${new}/linux/stack/runners.yaml"

    The command edits deploy/runners.yaml in place and exits with the number of conflicts, which it marks with <<<<<<< lines. Do the same for the other files that you copied. Take the entrypoint and the distributor script of the new release as they are unless you edited them, and rename their Swarm configs as Upgrade to a new release of this repository says.

  5. The keys that you are likely to have changed are deploy.replicas, image, deploy.placement.constraints, and deploy.resources. Check each one after the merge, and check the pin of the runner version and its SHA-256 values, which a release changes together, and the token proxy image, which a release names by digest.

  6. Check the result, and deploy with the same list of -c files as before:

    $ docker stack config -c deploy/runners.yaml > /dev/null
$ docker stack deploy -c deploy/runners.yaml runners

Swarm replaces the token proxy and updates the runner services one replica at a time. While the proxy is replaced, no new job is claimed, and every runner that had already claimed stays refused (Restart the proxy). To roll back, deploy the previous copy.

Troubleshooting

Refer to Troubleshooting. The most common problems on a first install are a missing secret, a node whose distributor cannot download the runner, and a task that stays pending because no node matches its constraints.

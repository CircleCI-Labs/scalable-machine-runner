Contributing

Thank you for helping to improve the machine runner swarm. This repository is part of CircleCI Labs. Field engineering reviews issues and pull requests on a best-effort basis and does not provide an SLA. CircleCI support does not cover this repository.

Reporting a bug

Search the existing issues first, and check that you use the latest release. Then open a new issue with the bug template. Include:

  • The release or commit of this repository, and the runner version. On Linux, run docker run --rm -v runners_runner-bin:/v:ro alpine cat /v/current/VERSION on the node. On Windows, run docker service logs --tail 100 runners_runner-distributor-windows.
  • The operating system of the node and the Docker Engine version.
  • The output of docker service ps --no-trunc runners_<service> and docker service logs --tail 100 runners_<service>.

Remove tokens, runner config files, and internal host names from everything you paste.

Security disclosure

Do not open a public issue for a security vulnerability. Email security@circleci.com and follow SECURITY.md.

Requesting a feature

Open an issue with the feature request template. Describe the problem you want to solve, and name the platform and the files it affects. For problems in the CircleCI platform or the runner agent, contact CircleCI support instead.

Opening a pull request

Before you open a pull request:

  1. Discuss large changes in an issue first.
  2. Run the tests for the platform you changed. Refer to Development.
  3. Update the documentation in docs/ when you change a variable, label, secret, port, or default.
  4. Write every commit message, and the pull request title, as a Conventional Commit. The release notes are generated from them, so there is no changelog entry to add. Refer to Commit messages.
  5. Check that the diff has no tokens, host names, or customer or vendor names. The repository is public.

A pull request from a fork gets no CI. The project builds no forked pull request and passes no secret to one, because the code of a fork would otherwise run with this project’s settings (Secrets and public logs). A maintainer reads the change, and to run CI on it pushes its commits to a branch of this repository by hand. Never push or mirror an outside branch to main or to a branch named smr-swarm/*: those two names get the e2e runner tokens and, on main, the publishing contexts, and the configuration of a job comes from its own branch.

A pull request that changes only documentation (docs/, site/, Markdown files) runs the lint jobs and the docs site build, and skips the builds and the Swarm tests (Documentation-only changes).

Use the pull request template. Maintainers choose the merge method for each pull request. A squash merge turns the pull request title into the commit message on main, and a merge commit or a rebase keeps your commits. Refer to Merge method.

Commit messages

Use Conventional Commits: type(scope): summary. The release job reads these messages to choose the version and to write the release notes.

TypeUse for
featA new capability, or a changed stack-file contract
fixA bug fix
docsDocumentation only
testTests only
ciThe CircleCI pipeline
choreMaintenance with no user-visible change
refactor, perfCode changes that keep behavior, or improve speed

Common scopes are linux, windows, docs, readme, and ci.

A breaking change appears first in the release notes. Mark it in the commit message, in one of two ways, and write what the user has to change:

  • Add ! after the type or scope: feat(linux)!: rename the persistent service.

  • Add a BREAKING CHANGE: footer:

    feat(linux): rename the persistent service

BREAKING CHANGE: the service is now linux-persistent. Rename it in your stack file.

While the version is 0.x, a breaking change raises the minor number.

Keep each commit small and atomic.

Development

Requirements: Docker with privileged containers for the Linux suite, bash, and PowerShell 7 for the Windows unit tests.

linux/tests/run-all.sh                 # the whole Linux suite, a Swarm inside Docker-in-Docker
linux/tests/run-all.sh token drain     # a subset
linux/tests/stack-config.sh            # stack file contract, no daemon needed
pwsh -File windows/tests/Invoke-UnitTests.ps1 -InstallModules     # PSScriptAnalyzer and Pester

The Linux tests run a Swarm inside docker:dind containers, so your own Docker engine never enters Swarm mode. The Windows Swarm tests run on a Windows host, and the CI pipeline runs them on Windows Server 2022 and 2025. Refer to CI/CD for the pipeline and for every lint command.

Each Linux test prints RESULT lines and exits 0 when it passes. run-all.sh runs all of them against one shared pair of Docker-in-Docker containers.

CI runs the groups as four parallel jobs, each with its own list of groups (linux-swarm in .circleci/continue.yml). A new test goes into all in run-all.sh and into one of those lists; lint-circleci fails when a group is in no list or in two. Refer to CI/CD for the lists and their durations.

The suite needs no installed runner. The distributor of the shipped stack installs it, as it does for a user, from a small HTTP mirror in the harness: a manifest.json and the tarballs of the versions that a test publishes (publish_runner in lib.sh). ephemerality.sh, persistent.sh, limits.sh, network.sh, and drain.sh publish fake-runner.sh, a stand-in for circleci-runner that runs a fake job through the step-down and exits, as a single-task runner does. task.sh, token.sh, exit80.sh, placement.sh, distributor.sh, and the idle case of drain.sh publish the real runner binary, which the harness downloads once and checks against the SHA-256 of CircleCI’s manifest.

Three variables change the setup. SWARM_TEST_DIND_IMAGE sets the Docker-in-Docker image. SWARM_TEST_CACHE sets the directory that caches the real runner binary, ~/.cache/swarm-tests by default. SWARM_TEST_KEEP=1 keeps the Docker-in-Docker containers for debugging.

The Windows tests in windows/tests print CHECK <name> PASS|FAIL lines and one RESULT line, and exit 0 only when every check passes. Invoke-UnitTests.ps1 runs the Pester tests on any system with PowerShell 7. The Test-*.ps1 scripts need a Windows host with Docker in Windows-container mode, and none of them needs a runner token.

Swarm config names

The entrypoint and the distributor scripts reach the nodes as Swarm configs. A Swarm config cannot change, and a service keeps the old file when the name stays, so the name of each config in the stack files carries the first 12 hex digits of the SHA-256 of its file. After you change linux/stack/circleci-runner-entrypoint, linux/stack/runner-distributor.sh, or windows/runner-distributor.ps1, run ci/config-names.sh --write and commit the new names with the change. lint-stack, linux/tests/stack-config.sh, and the release job run ci/config-names.sh and fail on a stale name. Nobody decides when to bump a number.

Documentation checks

Documentation follows the CircleCI docs style: sentence-case headings, active voice, no contractions, and short sentences. Every docs/*.md page has front matter with page-title, page-audience, and page-description.

CI checks the relative links and the Mermaid diagrams. To run the same checks locally:

docker run --rm -v "$PWD:/input" -w /input lycheeverse/lychee:0.24.2 --config lychee.toml './**/*.md'
docker run --rm -v "$PWD:/workdir" davidanson/markdownlint-cli2:v0.18.1 '**/*.md'

Pinned versions

Renovate opens a pull request every Monday for the pinned versions: the images and their digests, the tools that CI downloads, the Go toolchain and the docs theme. The configuration is renovate.json, and Pinned versions lists what it covers and what stays by hand. A pull request with the label checksum changes a version that is pinned with a SHA-256 value: Renovate cannot compute the value, so replace it in the same branch before you merge.

Pin images by tag and digest, and a new download by its version and checksum together, with a # renovate: comment above the version (see the page above). The runner version that the stack files install by default is pinned, in three places that must stay equal (linux/stack/runners.yaml, linux/stack/microvm.yaml and windows/stack/runners.yaml): the newest version that CI tests, bumped by each release (how). The alpine:3 image of the distributor is pinned by digest in linux/stack/runners.yaml. The pinned Git and 7-Zip versions and their SHA-256 values are in windows/stack/runner-distributor.ps1, and a change of the script needs ci/config-names.sh --write. Pin images by tag and digest.

Releases

Maintainers do not tag releases by hand, and nobody edits a changelog. Refer to Releasing for the details.

  • Versioning. The project follows Semantic Versioning and starts at 0.x. While the version is 0.x, a breaking change bumps the minor number. Version 1.0.0 is reserved for general availability or official adoption.
  • Release job. A CircleCI job runs on main after every test job of that pipeline has passed. git-cliff reads the Conventional Commits since the last release tag and computes the next version, with the rules in cliff.toml. A fix is a patch. A feat is a minor. A breaking change is a minor in 0.x and a major from 1.0.0. A push that holds only docs, test, ci, chore, style, or refactor commits makes no release.
  • Contents. Each release is a GitHub release with a tar.gz and a zip bundle of the user-facing files, a SHA256SUMS file, and a keyless cosign signature of that file, made with the CircleCI OIDC token. The release notes are generated from the commits, with breaking changes first. The job creates the tag through the GitHub API and never pushes a commit to main.
  • Changelog. CHANGELOG.md is a short page. The release bundle contains a generated CHANGELOG.md with every release.
  • Failures. If a release fails part way, a maintainer reruns the job in CircleCI. The job finishes the release at the same commit and never creates a second one.

Refer to Verify a release to check a download.

When the repository moves to CircleCI-Public

Replace the Labs wording in these files: the banner and the Support section of README.md, SECURITY.md, the support paragraph at the top of this file, .github/ISSUE_TEMPLATE/config.yml, and .github/CODEOWNERS. Decide the license, because CircleCI runner repositories use Apache-2.0 and this one uses MIT.

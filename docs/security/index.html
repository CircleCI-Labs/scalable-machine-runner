Security

Security

This page describes what the stack protects, what it does not protect, and which controls you must apply on the CircleCI side. Read it before you give a class to a team.

Important

Untrusted jobs on a self-hosted runner pose significant risks to your machines and your network. Never use self-hosted runners for public projects that build forked pull requests.

Status. This is a CircleCI Labs project at version 0.x. It has not been independently reviewed or penetration-tested. The documentation site follows the main branch, so it can describe a control that your release does not have: the copy of this page in your release bundle is the one for that release. What is tested says how each claim is checked, and which claims are not.

Threat model

What the stack protects

AssetWhere it lives
The runner token of a classA Swarm secret. The token proxy holds it for the single-task classes, so no runner container has it. A persistent class puts it in a file in each runner container
Job secrets, such as contexts and project variablesThe job environment while a job runs
Source codeThe working directory of a job
The node and its networkThe host, reachable from the containers by default egress

Who can attack

  • A job author whose code runs in your container, which is the normal case. The job can do anything its user can do.
  • A dependency or script that a job downloads and runs.
  • A forked pull request, when you allow fork builds on a public project. Do not allow it.
  • Another job that ran earlier on the same node, or that runs next to it.

Token model on each OS

A resource class token only authorizes a runner to claim tasks for that class. A holder of the token can still run a runner of their own on that class, and claim jobs that were meant for yours. That gives them the code and secrets of those jobs, so treat the token as a secret and rotate it.

The two arrows into the runner and the API show the two paths. A single-task class takes the first, on Linux and on Windows: the runner talks to the proxy, and only the proxy holds the class token. A persistent class takes the second: the runner holds the token itself.

Linux

  • Single-task classes: the token proxy. The class secret <service>-token is mounted into the token-proxy service and nowhere else. The runners read a made-up placeholder config, and the proxy adds the class token to their claims. A job cannot read what the container does not hold, so the sudo setting no longer decides whether a job can reach the class token. Refer to The token proxy.
  • Storage. A class secret is a minimal runner config file that holds only api.auth_token. Swarm mounts it as a read-only file in memory, in the proxy container at /run/secrets/<service>-token (uid 65534, mode 0400), or, in a persistent class, in the runner container at /run/secrets/circleci_runner_config.yaml, owned by the runner user circleci-runner (uid 2000) with mode 0400. The runners of the other classes mount the placeholder secret runner-placeholder-token at the same path. The runner reads it with --config. The token is in no environment variable, no command line, and no stack file, and docker inspect does not show it.
  • Users. The runner runs as circleci-runner, which has no sudo rights and cannot write to /opt/machine-runner-swarm. Jobs run as the job user, stepped down with command_prefix.
  • Default class. The job user keeps passwordless sudo. A job that uses sudo is root in its container. It can read the placeholder, the files of the runner, and become the runner user, but the container holds no class token. What a job still gets is the task token of its own job, which the task agent already has.
  • Hardened class. MACHINE_RUNNER_SWARM_JOB_SUDO: "false" steps every job down with setpriv --no-new-privs, even when the image has sudo, and the container does not start when the image has no util-linux setpriv. The entrypoint edits no file: Swarm ignores no-new-privileges, so this per-job flag, inherited by everything the job starts, is what stops a setuid binary (sudo with its rules intact, su, or one with a local-root bug) from lifting a job to root. The job also gets none of the CIRCLECI_RUNNER_* and MACHINE_RUNNER_SWARM_* variables of the container. The job user cannot read the file or the process of the runner, and cannot become another user. A kernel or container-runtime bug can still lift a job to root, because the containers share the host kernel. Tools must be in the image. Use this for shared or regulated classes, and for the persistent class when its jobs can do without sudo.

The test linux/tests/token.sh measures the probes below against the real runner binary, with the sentinel token in the runner’s config file as the persistent class has it. The test linux/tests/proxy.sh shows that, with the proxy, no class token is in a runner container: it scans the files, /proc/*/environ, and /proc/*/cmdline of the runners as root.

Windows

  • Single-task classes: the token proxy. The class secret <service>-token is mounted into the service token-proxy-windows and nowhere else. The runners read a made-up placeholder config, and the proxy adds the class token to their claims, as on Linux. Refer to The token proxy.
  • Storage. A class secret is the same minimal runner config file. Swarm places it at C:\ProgramData\Docker\secrets\<target> (in the proxy container <service>-token, in the runner container of the persistent class circleci_runner_config.yaml). Windows does not support uid, gid, or mode for secrets, and only administrators and SYSTEM can read the file.
  • No step-down. The runner and the jobs run as ContainerAdministrator, because the runner needs its symbolic link privilege. A job can read the config file of its runner, which holds the placeholder (in a persistent class: the token). The token is not in the job environment. An administrator in a container has no dropped NET_RAW, so the guarantee of the proxy that a job cannot forge a source address does not hold on Windows the way it does on Linux. What a forged address gets the job is limited: the answer to a claim goes to the owner of the address, not to the sender, and a container that has claimed cannot claim again. Windows is not tested for this, so treat each class as a trust boundary all the same.
  • Clear text on disk. The token is stored as plain text on the disk of the container of the proxy (and of the runner, in a persistent class). Swarm writes the secret to the root disk of the container, and keeps it there until the container stops. This is a limitation of Swarm on Windows. On Linux, the secret is a mount in memory (tmpfs) and never reaches the disk of the container. Anyone who can read the Docker root directory of the host can read a Windows token, so enable BitLocker on the volume that holds it. Refer to BitLocker on Windows hosts.
  • What the proxy gives on Windows. The proxy keeps the class token out of the job environment and out of the file system that the job sees. It is not a boundary against a hostile job on the same host: a job runs as an administrator, with process isolation, next to the proxy when both run on one node. It becomes a boundary only when the proxy runs on a node that runs no jobs (in a cluster, label that node machine-runner-swarm.proxy=true: runner services never run on a node with that label), and untrusted classes run with Hyper-V isolation, which is not tested here. The end-to-end jobs on Windows run real jobs through the proxy, but they only record whether a job can read the token and assert nothing about it, and no test forges a source address, so treat these protections as untested.
  • Process isolation. Microsoft does not treat process isolation as a security boundary. Use one trust group of classes for each host. Hyper-V isolation adds a kernel boundary, needs nested virtualization on a virtual machine, and is not tested here.

Treat each Windows resource class as a trust boundary. Use one token for each class and host, restrict who can use the class, and rotate tokens.

Swarm

  • Swarm stores secrets encrypted in the Raft log of the managers, and sends a secret only to nodes that run a task that uses it.
  • Optionally lock the managers with docker swarm update --autolock=true. It protects the secrets at rest, but each manager then needs docker swarm unlock after every Docker daemon restart.
  • Keep join tokens private, and rotate them with docker swarm join-token --rotate.
  • A user in the docker group on a manager can read every token. Limit administrator access to the managers.

The token proxy

The service token-proxy in runners.yaml keeps the class tokens of the Linux single-task classes away from the runner containers and from the jobs that run in them. One proxy serves every class of the stack, and docker-build.yaml and ssh-rerun.yaml add their classes to it. Refer to Concepts for how the pieces fit.

What it does:

  • The claim is the only call that gets the class token. The runners send every API call to the proxy and hold a made-up token. The proxy replaces the Authorization header of the task-claim call (POST /api/v3/runner/claim) with the class token and passes every other call on unchanged. The runner and its task agent use the task token from the claim response for the rest, and the token is scoped to one task.
  • The class is decided by the network, not by the caller. The proxy finds its classes in its own secrets directory: every secret <service>-token is the class <service>, whose runners are tasks.<service>. The made-up secret runner-placeholder-token is never a class, and no runner token is mounted into the proxy. A claim is allowed only from an IP address that Swarm DNS lists now for tasks.<service> of a class, and it gets the token of that class. Any other address, such as a container that you started on the class network, gets 403 and nothing reaches CircleCI. An address that two classes list is refused too. The 403 says only claim refused: the reason, with what DNS lists, is in the log of the proxy and nowhere a job can read it.
  • One claim per container. After a claim that returns a task, that address cannot claim again until DNS has not listed it for 30 seconds in a row, which means the container is gone. One missing answer, even a no such host for the whole class, is one poll of the 30 and never a release. A job that runs in a container cannot use the proxy to claim again for itself or to start more tasks of its class.
  • The source address cannot be forged by a job. The proxy attaches to each class overlay network with endpoint_mode: dnsrr, so it sees the address of the container that connects, not an address that the Swarm load balancer rewrote. The runner services drop NET_RAW, so even root in a container cannot send packets with another address. The encrypted class networks need Docker Engine 23.0.3 or later (or 20.10.24): earlier engines accepted unauthenticated VXLAN traffic on encrypted overlay networks (CVE-2023-28840), which would let a host on the node network inject packets into a class overlay. The setup helper requires Docker 24 or later. Keep cap_drop: [NET_RAW, MKNOD] or ALL on every class that uses the proxy. The one exception is linux-microvm-docker, which cannot drop it (BuildKit needs it): it runs in a VM with no NET_ADMIN, stays at one replica, and has an overlay of its own, so there is no other runner of its class to impersonate (MicroVM jobs).
  • It knows who has claimed, also after a restart. The proxy writes the addresses that have claimed to the small volume proxy-state before the runner gets its task. If it cannot write them, the claim fails and the runner does not get the task, and the proxy removes the state file (and keeps its marker), so that its next start takes the fail-safe path below instead of reading a state that is behind. A restart with a state refuses every address in it, whether Swarm DNS lists that address yet or not, and only those, so a runner that started before the proxy, or waited through a restart, is never locked out. A start with no state (an empty proxy-state, a state that was lost, or a class that is new) does not guess: for each class the proxy asks CircleCI (GET /api/v3/runner/scale, with the token of that class) how many tasks run. With none running, no runner present can hold a job, and they may claim. With some running, or when the call fails, the proxy refuses every runner of that class present until Swarm replaces it, so a runner that holds a job cannot claim another after a failover. The state stays on the node, so if the proxy moves to another node, it starts empty there: refer to Where the proxy runs, and when it moves for what to do. The service runs on a manager by default, and you can pin it to the node that keeps the volume with the label machine-runner-swarm.proxy=true and the placement variable.
  • A claim with an unknown outcome counts as a claim. When the request reached CircleCI but the answer was lost (a timeout, a broken connection), the proxy cannot know whether CircleCI handed the runner a task. It latches the runner as if the claim had succeeded, so that runner is refused until Swarm replaces it. This costs a runner, never a second task for one container. The proxy waits at most 60 seconds for the response headers of the upstream.
  • It fails closed otherwise. The proxy does not start without a usable token file for every class, nor when it cannot write its state. It answers 503 when DNS fails, when a token file disappears or when it cannot write its state. A count of running tasks that CircleCI does not give as a whole number of 0 or more (data.attributes.running_task_count and unclaimed_task_count, exactly these names), or does not give in 25 seconds for all classes together, counts as running tasks. It logs addresses, class names, and status codes, never a token.
  • It limits what a job can send it. A claim is accepted from one address at most twice a second, with bursts of 10 (a runner claims about every 5 seconds), and its body is at most 64 KiB. The server has timeouts for the request header, the whole request and an idle connection, and caps the size of the headers. A runner that has claimed, or has a claim in flight, is refused from memory with no DNS lookup, and the lookups of all other claims share one answer for a second, so a job that floods the proxy with claims cannot make claims of other classes fail. Besides the claim limit, every client address is limited to 50 requests a second, with bursts of 200, on all paths, and the proxy serves at most 512 requests at the same time: more get a 503 with a Retry-After header. The proxy logs one summary line a minute: the claims it forwarded, the claims it latched, and the claims it refused, by reason. These limits keep one runner from starving the rest, and they do not make the proxy proof against a hostile job: the 512 shared slots and the one replica can still be used up by a job that sends enough requests from the containers of its class, and the claims of every class then wait. Watch the log line and Monitor the token proxy.
  • It is small and locked down. One static Go binary, in a published image on a minimal base (distroless static: CA certificates, no shell, no package manager), runs as uid 65534 with no capabilities, a read-only root filesystem and no published port. The image is signed, and a release pins it by digest: refer to The token proxy image. Its secrets are the class tokens and nothing else.

What it does not do:

  • It sees the runner traffic of its classes. The runner and the task agent send their API calls through it, over plain HTTP on the overlay network: claims, task configuration, and step output. The class token is never on that path, but the task token is. Between nodes, the Linux class networks are encrypted by default (driver_opts: {encrypted: "true"}, IPsec between the nodes, which needs IP protocol 50 (ESP) open between them: refer to Encrypted class networks), so the task tokens and the step output do not cross the network of the nodes in clear text, and a host on that network cannot inject packets into a class overlay. Docker does not support encrypted overlay networks for Windows containers, so the Windows class traffic is plain between nodes: keep the Windows nodes on a network that you trust.
  • It is one point of failure. One replica serves all classes, because a second replica would not share the record of who has claimed. While it is down, no runner can claim. A job that is running keeps its container and its calls wait for the proxy. Refer to Monitor the token proxy.
  • The node of the proxy holds every class token. A job that escapes its container onto that node reads them. The proxy never runs on a Docker-build node or on a node of the container agent, which holds the Docker socket. It runs on a manager by default. In a cluster, label the node that runs it with machine-runner-swarm.proxy=true: runner services never run on a node with that label, so a job never shares a node with the proxy. On a single node there is no such label, nothing changes, and the jobs run next to the proxy. With several managers, pin the proxy to one with the label and MACHINE_RUNNER_SWARM_PROXY_PLACEMENT.
  • It depends on the runner API. The proxy knows two runner API calls: POST /api/v3/runner/claim, and GET /api/v3/runner/scale with the fields running_task_count and unclaimed_task_count. They are tested against the runner version that this release pins. If CircleCI changes them, the proxy fails closed and jobs wait until a release of this project follows the change. Pin the runner version in production. This page makes no claim about how the Runner Terms apply to a proxy between your runners and CircleCI: that is for your own review.
  • It does not cover the persistent classes. Refer to The persistent class.
  • Windows has its own proxy. The Windows stack runs token-proxy-windows (the windows/amd64 image of the same tag) for the Windows classes, because a Windows node does not share its network with a Linux proxy. It works as described here, with the differences in Windows. There is no windows/arm64 image (Windows).
  • It does not replace CircleCI-side controls. A stolen class token still lets its holder run a runner on that class. Rotate tokens and restrict classes to projects, as in CircleCI-side controls.

The persistent class

A persistent class (persistent.yaml) does not use the proxy. A continuous runner claims a task after every job, and the proxy allows one claim for each container, so the runner keeps its token in a file in its own container. This class is weaker than the proxied classes:

  • The shipped file sets MACHINE_RUNNER_SWARM_JOB_SUDO: "false", so the token file is unreadable to the job user, and the tools that jobs need must be in the image. If you set "true" (the opt-in), a job that uses sudo reads the class token, and it can then run a runner of its own on that class.
  • State from one job is visible to the next, because the container lives on.

Therefore give the persistent class a resource class of its own, restrict it to trusted projects with a config policy, keep production contexts away from it, and rotate its token on a schedule. Refer to Persistent mode.

Runner binary integrity on Linux

The runner executes the jobs of your classes, so it must be the binary that CircleCI published. The runner-distributor service installs it, and the entrypoint checks it before every start. Refer to The runner distributor on Linux for how the parts fit.

Where the runner comes from

The distributor downloads the tarball over HTTPS from the release bucket of CircleCI. By default it compares the SHA-256 of the tarball with the values that the stack file carries for the pinned version (MACHINE_RUNNER_SWARM_RUNNER_SHA256: amd64, arm64, ppc64le and s390x, taken from CircleCI’s manifest when the version was bumped, and reviewed with the release of this repository). The manifest is not asked, so a change of the bucket after the bump cannot change what the nodes install. Each release of this repository bumps the version and its values together. The values are copied from CircleCI’s manifest when the version is bumped, so this is trust on first use from the same bucket: CircleCI publishes no signature for the runner that this stack checks.

A floating value (3.1, 3, current) cannot have such a list, because the version is not known in advance. The distributor ignores the default list of the pin and compares the SHA-256 with the value in the manifest.json of CircleCI, which it also gets over HTTPS. This is weaker: the manifest comes from the same bucket as the tarball, so whoever can change one can change the other, and the check proves that the download is whole, not that CircleCI published it. It is the same trust as the runner’s own download of the task agent, which every container fetches from the same bucket. An exact version of your own needs its own list, from the checksums.txt of its release (the tarballs of every architecture of your nodes), or the word manifest. The distributor then installs only a tarball that matches.

MACHINE_RUNNER_SWARM_DOWNLOAD_BASE_URL, the address of a mirror, must be an https:// URL unless a usable SHA-256 list is set for an exact pin: over plain http the manifest could be changed on the way, and with it the hash that it names. A floating value has no list, so an http:// base is refused unless MACHINE_RUNNER_SWARM_ALLOW_HTTP=true. The microVM classes download the runner into every VM with the same rules.

The token proxy image

The token proxy is not installed by the distributor: it is the image ccilabs/machine-runner-swarm-proxy of Docker Hub, which Swarm pulls. Its integrity rests on the image digest, not on a volume. A release bundle names the image by tag and digest (ccilabs/machine-runner-swarm-proxy:<version>@sha256:<digest>), so Docker pulls exactly the image that the release pipeline pushed, whatever happens to the tag later. A checkout names the tag latest, which only a release moves and which is not a digest: pin a digest for anything that matters (Upgrade the token proxy). linux/setup.sh --deploy prints a warning when MACHINE_RUNNER_SWARM_PROXY_IMAGE is not pinned by digest. ccilabs is the Docker Hub organization of CircleCI Labs. The name is not what you trust: the signature below is, and an image of that name that does not verify is not this project’s.

Every digest that the pipeline pushes is signed, and the pipeline checks the signature of the image again before it gives the image its release tags. The Linux index (four platforms), each Windows image (Server 2022 and 2025) and the manifest list that joins them are signed separately, so you can verify the list that you name or the image of one platform. The image runs as the user 65534 (Windows: ContainerAdministrator, because a Windows volume has no user mapping), and the state of the proxy is the only thing it writes.

Verify the token proxy image

The signature is a keyless cosign signature, made with the OIDC token of the CircleCI job that pushed the image, like the signature of a release (Verify a release). It proves that a job of this CircleCI project pushed that digest. Verify the digest that you run, before you run it. You need cosign 3.1.3 or a later 3.x (CI signs and verifies with 3.1.3, and earlier versions are not tested). A digest of the manifest list covers every platform; pass the tag, and cosign resolves it to the digest and prints it.

cosign verify ccilabs/machine-runner-swarm-proxy:<version> \
  --certificate-identity "https://circleci.com/api/v2/projects/7bbdbb66-6ba8-4f6c-982e-d4fb401ec257/pipeline-definitions/8b2a66db-3f28-5c80-88e4-03f4694b5b60" \
  --certificate-oidc-issuer "https://oidc.circleci.com"

The command prints the verified claims as JSON when the project and the pipeline definition above signed the image. This is only the signature check. It does not look at the ref, so a reader who stops here accepts an image that a job of any branch signed: the ref check below is a second, separate step. Compare the digest in its output with the one in your stack file. A tag from a commit that is not a release (edge, sha-<12 characters>) verifies the same way. The identity does not name a branch, and a job of any branch can sign with it, so also check the ref in the certificates: the extension 1.3.6.1.4.1.57264.1.14 must be refs/heads/main, for every signature of the digest. cosign has no flag for that extension, so the command reads it, with the same pattern as Verify a release (the OID, then the value refs/heads/main, from a byte boundary):

cosign download signature ccilabs/machine-runner-swarm-proxy:<version> \
  | jq -r '.verificationMaterial | (.certificate // .x509CertificateChain.certificates[0]).rawBytes' \
  | while read -r cert; do printf '%s' "$cert" | base64 -d | od -An -v -tx1 | tr -d ' \n' \
    | grep -Eq '^([0-9a-f]{2})*2b0601040183bf30010e0411(0c|13)0f726566732f68656164732f6d61696e' \
    || { echo "NOT signed for refs/heads/main: do not use this image"; exit 1; }; done && echo "every signature is for refs/heads/main"

The notes of every release name the image of that release.

What remains

Not verified by this stack:

  • The task agent, which every container downloads from the same bucket at start, with no pin and no check. It runs as the job user and holds the task token.
  • The source of the pinned SHA-256 values: CircleCI’s manifest at the time of the bump.
  • The gap between the hash check and the exec of one container start (the next point).

Also:

  • A privileged sibling container with SYS_ADMIN on the same node could mount the volume read-write and change both the binary and its record. The microVM classes do not mount the volume for this reason: each VM downloads and verifies its own runner. Refer to MicroVM jobs.
  • The check at the start of a container narrows the window and does not close it: a sibling that rewrites the file between the hash and the exec of one start is not detected.
  • The docker-build class mounts the Docker socket of the host and is root-equivalent on its node, so it can change the volume too. Refer to Docker Builds.
  • Whoever can update the runner-distributor service, for example a user in the docker group of a manager, chooses the version and the download address. A list in MACHINE_RUNNER_SWARM_RUNNER_SHA256 limits what can be installed to the tarballs on it.

Runner binary integrity on Windows

The trust is the one of Linux: the service runner-distributor-windows downloads the tarball over HTTPS from the release bucket of CircleCI, compares its SHA-256 with the two values (amd64 and arm64) that the stack file carries for the pinned version (a floating value ignores that list and uses the manifest.json of CircleCI, which is weaker, as on Linux; a mirror must be https:// unless a usable list is set for an exact pin, or MACHINE_RUNNER_SWARM_ALLOW_HTTP=true when there is no list), checks that the binary reports the version, and records the SHA-256 of the binary in versions\<version>\SHA256. Portable Git and 7zr.exe are pinned by SHA-256 in the script, so a new Git version is a new script and a new release of this repository.

Two things differ. The runner is the main process of the container and there is no entrypoint, so nothing checks the binary when a container starts. The distributor compares the active binary with its record at every check interval (24 hours by default) and installs it again when it changed. And a job runs as an administrator, but in its own container: the volume is mounted read-only through two links, so a job cannot change the runner or Git. A container with write access to the volume, for example one of the docker-build class (it controls the engine and is root-equivalent on its node), can still change them. Refer to Docker Builds.

Read the table this way:

  • The token. According to its documentation, in the orchestrator the token never reaches the VM, so even a root job cannot read it. What differs is that a job that escapes its container onto the node of the proxy reaches the tokens, where in the orchestrator the sidecar is next to a virtual machine. No test asserts that on Windows, and it is not a boundary against a hostile job on the same host as the proxy (refer to Windows). The persistent class is at parity with the official Windows runner: the job can read the token. The Windows classes have no hardened variant. Treat each Windows class as a trust boundary.

Working directory cleanup

The runner can remove its working directory before it starts a task and again after the task. On Linux, the stack files and the entrypoint turn this off with CIRCLECI_RUNNER_CLEANUP_WORK_DIR: "false".

The reason is file ownership. The runner runs as the runner user (uid 2000), and the working directory and the files in it belong to the job user. The runner cannot remove them, so with cleanup on every task fails before it starts. The log shows failed to remove working directory before starting task with permission denied, even for the first task, because the parent directory belongs to the job user too. Giving the runner user the ownership does not help, because the job user must then be able to create the directory again. Running jobs as the runner user would give every job the runner token and remove the step-down, so the stack does not do that.

What this means for each class:

  • Single-task classes. Nothing is lost. Swarm discards the container after the job, so no file survives.
  • Persistent classes. Nothing removes what a job leaves in the working directory, and the next job can read it. Start every job with a step that removes what an earlier job left. Recycle the class on a schedule. Refer to Persistent mode.

Do not set the variable to true on Linux. Refer to Error: failed to remove working directory. Windows jobs and the runner use the same account, so the Windows files keep cleanup on.

Isolation between runners

Replicas of one class share an overlay network and can reach each other. Swarm cannot prevent this: enable_icc=false is ignored on swarm-scoped networks, overlay networks have no such option, and a stack cannot use a node-local bridge network. On Windows, the overlay is the only network option for services, and Windows has no equivalent control for it. All Windows classes share one overlay network of the stack, and it is not encrypted, so Windows classes can reach each other, and their traffic is in clear text between nodes (Encrypted class networks).

On Linux, each class gets its own overlay network, so classes cannot reach each other. Containers can still reach the host network and the internet through default egress. To reduce the exposure:

  • Run sensitive classes on dedicated nodes. Refer to Multi-Node Clusters.
  • Treat the proxy as part of every class network: any container on a class network can reach it, and the proxy answers only claims from the runners of the class.
  • Filter egress on the host, for example in the DOCKER-USER chain on Linux. Docker bypasses ufw and firewalld rules for published ports and for container traffic, so a rule in either of those does not filter it.
  • Rely on single-use containers. A compromised replica disappears with its job.

Cloud nodes: block the metadata address

A job runs in a container on your node, and nothing in this stack or in Docker stops it from sending traffic to the instance-metadata service that cloud providers serve at the link-local address 169.254.169.254. On a cloud virtual machine, that service can hand out the credentials of the role that is attached to the node and, on some clouds, the user data of the instance. A job that reads them acts as the node. This is true of every self-hosted runner on a cloud VM, and it is not specific to Swarm. The recipes below are the usual ones. They are not tested in this repository’s CI: check them on your own nodes with a job that runs curl -m 3 http://169.254.169.254/ and must fail.

  1. Give the node role the fewest permissions that the node needs, which is often none. Do not leave the Swarm join token readable in the user data or the startup script of an instance, because any job that reaches the metadata service reads it, and with it joins a node to your Swarm.

  2. Block the address for containers on Linux. Add a rule to the DOCKER-USER chain, which Docker evaluates before its own rules for container traffic:

    sudo iptables -I DOCKER-USER -d 169.254.169.254 -j DROP

    Docker creates the chain when it starts, so the rule must be added after Docker is up, and again after a reboot: put it in a systemd unit that starts after docker.service. The unit adds the rule only when it is missing.

    [Unit]
Description=Block the instance metadata address for containers
After=docker.service
Requires=docker.service

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/bin/sh -c 'iptables -C DOCKER-USER -d 169.254.169.254 -j DROP 2>/dev/null || iptables -I DOCKER-USER -d 169.254.169.254 -j DROP'

[Install]
WantedBy=multi-user.target

    The rule does not cover a container on the host network, which the docker-build class can use, and it does not cover the host itself. Check it with sudo iptables -S DOCKER-USER after a reboot and after a restart of Docker. If your Docker uses another firewall backend, use its equivalent of the rule.

  3. On AWS, require IMDSv2 and a hop limit of 1. This disables IMDSv1 and stops the session-token response from reaching a container behind Docker’s bridge or NAT, because the extra hop exceeds the limit:

    aws ec2 modify-instance-metadata-options --instance-id <id> --http-tokens required --http-put-response-hop-limit 1 --http-endpoint enabled

    It does not cover containers on the host network. It also breaks every job that uses the node role through the metadata service: give such jobs their credentials another way, for example through a context or OIDC.

  4. On other clouds, apply the same two ideas. Allow the metadata service from the host only (the rule above), use the provider’s session or header requirement for it if it has one, and attach a role with minimal permissions. Refer to the documentation of your provider for the setting, because this page does not cover each cloud.

On Windows, this page has no rule that is tested. The role, user data and cloud-side settings above apply to a Windows node too, but have not been tried with Windows containers.

CircleCI-side controls

The stack cannot decide which projects may use a class. Apply these controls in your organization.

  1. One class and one token for each service. Give each token a nickname that names its host or purpose, so you can revoke it alone. Only organization admins create and delete resource classes. Delete the tokens of a class before you delete the class.

  2. Config policies. Restrict each class to named projects with the resource_class_by_project helper. Config policies need the Scale plan on cloud, or server version 4.2 or later. A class that is not in the mapping stays available to every project.

    package org
import data.circleci.config

policy_name["runner_policies"]

enable_hard["resource_class_check"]

resource_class_check = config.resource_class_by_project({
  "<namespace>/linux-hardened": {"<project ID>"},
  "<namespace>/linux-docker-build": {"<project ID>", "<project ID>"}
})

    Enable evaluation and push the policy. Refer to Config policies for self-hosted runner.

    $ circleci policy settings set --org <org> --enabled
$ circleci policy push ./config-policies --org <org>

  3. Context restrictions. Project restrictions, security groups, and expression restrictions combine with logical AND. Restrict every context that jobs on a runner class use. For deploy contexts, add an expression such as pipeline.git.branch == "main" and not job.ssh.enabled.

  4. No fork builds on public projects. CircleCI does not make self-hosted runners available to public projects that have Build forked pull requests enabled.

  5. SSH rerun stays off unless a class needs it. The shipped classes leave CIRCLECI_RUNNER_SSH_ADVERTISE_ADDR unset and publish no ports, so they cannot serve SSH. If you deploy the SSH add-on stack file, keep its class for named projects and restrict inbound port 54782 with the DOCKER-USER chain or a cloud security group, not with ufw or firewalld, which a published port bypasses. Refer to Rerun job with SSH.

  6. Monitoring. Watch the runner inventory for names you do not know, and the logs for 401 and for exit code 80. In the log of the token proxy, a claim that is refused comes from a container that is not a runner of a class, or from a runner that tries to claim twice. Refer to Monitor the token proxy.

Runner classes are usable only by jobs of the organization that owns them.

CircleCI server

CircleCI documents machine runner 3 for server 4.4 and later, and says that an install on server sets the API URL of the runner (CIRCLECI_RUNNER_API_URL, or api.url in the config file). This repository is tested against CircleCI cloud only. In this stack the runners send their calls to the token proxy, so the URL of your server goes to the -upstream argument of the token-proxy service (its command in the stack file), and the runners keep CIRCLECI_RUNNER_API_URL: http://token-proxy:8080. Whether the proxy and the runner download work against your server version is not known, and no job of this project has run against one. Config policies, which the CircleCI-side controls above use, need the Scale plan on cloud or server 4.2 or later.

BitLocker on Windows hosts

Docker keeps a Swarm secret in clear text on the container root disk until the container stops. Encrypt the volume that holds the Docker root directory, which is C:\ProgramData\docker by default, with BitLocker. Confirm the protection status:

Get-BitLockerVolume

The status of the volume must show that protection is on. BitLocker protects the token when someone steals the disk, or a snapshot or backup of it. It does not protect against a job, or an administrator who is logged in to the live host, because both read the decrypted file. Limit the local administrators of the host, use one token for each class and host, and rotate tokens. Refer to the Microsoft documentation for BitLocker on Windows Server for the setup steps, including the recovery key.

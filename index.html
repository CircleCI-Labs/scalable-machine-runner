Machine runner swarm

CircleCI machine runners on Docker Swarm, in containers

For platform teams that run Docker hosts or Windows Server and want a clean container for every job, without Kubernetes.

Start on Linux Start on Windows Server

CircleCI Labs project, pre-1.0. Not an official CircleCI product and not supported by CircleCI Support. Pre-release 0.x: a minor release can change stack files. Field engineers maintain it on a best-effort basis. Read the support notice.

Machine runners for the Docker hosts you already run

  • One service for each resource class

    A Swarm service is a resource class, and deploy.replicas sets how many runners it has. Labels and constraints decide which nodes run it.

    How a class maps to a service

  • A clean environment for every job

    By default a runner claims one job and exits, and Swarm starts a new one, so no job inherits files from an earlier job.

    What a clean environment covers

  • Linux and Windows Server

    Linux amd64 and arm64 and Windows Server 2022 and 2025 are tested with real jobs. Multi-node clusters are tested in CI on two-node Swarms; ppc64le and s390x only under emulation.

    Multi-node clusters

  • Hardening and a threat model

    A documented threat model and token model, a hardened class without sudo, and guidance on egress.

    Threat model

When to use it

  • You do not need machines of your own: use CircleCI cloud executors. Self-host only for what the cloud cannot give you, such as static IP addresses, access to a private network, IAM permissions on your own hosts, or an environment that CircleCI does not offer. CircleCI’s runner overview lists the use cases.
  • You run Kubernetes: use container runner. CircleCI documents it, and it runs jobs in pods.
  • You need a boundary stronger than a container, a full operating system, privileged or KVM jobs, or autoscaling: use the machine runner orchestrator. It runs each job in its own virtual machine on Kubernetes. This repository has an experimental microVM add-on for a similar need on Docker hosts. It is not proven with real jobs.
  • You want a runner on a host or in one container: use machine runner 3, or on Docker. Jobs share the host, or a container that is reused.
  • You run Docker hosts or Windows containers without Kubernetes, and want a clean container for every job: use this repository. It has no support from CircleCI, and the containers share the host kernel.

Do not use this repository when you need autoscaling or cloud node integration (the number of replicas is fixed, and the nodes are yours), CircleCI server, macOS, privileged or KVM jobs, or a host with no internet access. Capacity is fixed, so you pay for the peak, whether or not jobs are waiting. The product names and pages in this list were checked against circleci.com on 17 October 2026. The FAQ has the full comparison, and Security compares what a job can reach.

Known limits of this project:

  • Fixed capacity. Swarm has no autoscaling, and this project creates and removes no nodes. You choose the replicas, you run the nodes, and an idle replica holds its reservation. There is no metrics export: the signals are docker commands and log lines (Operations).
  • Availability. One token proxy runs on a manager, and every runner API call goes through it. While it is down, no new job starts, and Swarm restarts it. A production cluster needs three managers. This is not a high-availability product.
  • Shared kernel. Jobs run in containers. The default class gives jobs passwordless sudo.
  • Windows. Stopping a busy container from outside kills its job after about 5 seconds, the overlay network is not encrypted, and process isolation is not a security boundary.
  • Secrets. Class tokens are Swarm secrets, and a user in the docker group of a manager can read them. There is no external secret manager.
  • Not in this release: autoscaling, a metrics export, a hardened Windows class, CircleCI server, air-gapped installs, macOS.

Your first job

  1. Create a resource class and token with the CircleCI CLI (install the CLI, then circleci auth login).
  2. Follow Quickstart on Linux or Quickstart on Windows Server: download a release, verify it, deploy the stack, and run a sample workflow.
  3. Point a real workflow at your class. Start from examples/linux-hello.yml on GitHub.

Install paths, operations, and security are in the documentation.

Support

CircleCI support does not cover this repository. Field engineering handles issues on a best-effort basis, without an SLA. Open a GitHub issue for a bug or a feature request, or ask on CircleCI Discuss. Problems with the CircleCI platform or the runner agent go to CircleCI support. To report a security vulnerability, read SECURITY.md.
